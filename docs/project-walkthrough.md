# 项目导读：我到底做了什么，怎样讲清楚这套 Workbench

这是一份给项目发起人的说明。建议先读本页，再打开[产品案例](../case-study/portfolio-case.md)、[三屏原型](../prototype/index.html)和[本地演示](../app/README.md)。

## 一句话理解

你提出了一个 AI4Science 产品经理作品集方向：让研究者从**研究问题**出发，看到**可回到原文的文献线索**，自己核对后保存**证据卡片**。Codex 在你的授权下协助整理公开资料、写需求和原型、实现本地演示、运行离线检查并发布到 GitHub。这是**个人产品实践与受控演示**，目前没有真实用户访谈、上线产品或模型生成能力。

### 先认清三类内容

| 类型 | 这里是什么 | 可以怎样表述 |
| --- | --- | --- |
| 已完成事实 | 仓库中的文档、原型、程序、代码提交、真实运行的逐题 JSON 和浏览器冒烟检查。 | “我提出方向并与 Codex 协作完成原型；在固定题集上运行了程序检查。” |
| 有出处的二手资料 | 别人发表的访谈/调查、竞品官方功能说明、两篇公开综述。见[二手研究](../research/secondary-research.md)、[竞品桌面研究](../research/competitor-desk-review.md)和[数据说明](../data/README.md)。 | “公开研究提示了可能的问题；还需要验证是否适用于我的目标用户。” |
| 待验证假设 | 医学影像研究者是否需要这套流程、能否更快或更准确完成任务、是否愿意持续使用。 | “这是待访谈和可用性测试检验的假设。” |

公开论文中的受访者**不是**本项目招募的用户；题集分数**不是**用户满意度、AI 准确率或上线成效。

## 项目是怎样一步步做出来的

### 1. 先保存科研记录骨架

已有仓库保留了 [README](../README.md)、[科研工作流程](workflow.md)、`templates/` 中的文献/实验/证据/复现模板、`records/` 存放约定和数据管理说明。这些材料面向未来的**科研记录**，没有被产品文档覆盖。Git 提交记录从 `1373df2` 的记录基础开始；后续成果在其上逐步增加。

### 2. 把大目标收敛为一个可演示任务

“自动检索论文、整理实验、辅助复现”范围太大，所以第一阶段只做“问题 → 来源 → 卡片”。[问题定义](../product/problem-brief.md)写目标用户和待验证问题；[PRD](../product/PRD.md)写范围、优先级与可检查的验收条件；[用户流程](../product/user-flow.md)写正常与异常路径；[决策记录](../product/decision-log.md)解释为什么先用少量受控资料。

这里的核心取舍是：**看不到足够来源时明确说没有找到**。内置摘要只充当检索线索，不能替代用户核对论文原文。

### 3. 用公开资料建立设计依据

[二手研究](../research/secondary-research.md)引用了已发表的研究者访谈和调查；[竞品桌面研究](../research/competitor-desk-review.md)依据产品官方文档梳理功能。这是选题依据，尚不是对本产品的需求验证。[访谈提纲](../research/interview-guide.md)和[竞品同题分析框架](../research/competitor-review.md)是未来实测的工具，当前没有填入虚构的受访者或实测结果。

演示资料只取自[两篇公开综述](../data/README.md)：仓库保存书目信息、原文链接、章节定位和 8 条人工写的中文概述，不收录论文全文、患者影像或 BraTS 数据集。论文页面标注的 CC BY 4.0 不等于 BraTS 数据集本身可以随意分发。

### 4. 先画交互，再做可运行演示

[三屏原型](../prototype/index.html)让你点击体验问题、来源、卡片和无答案路径。[应用](../app/README.md)是实际可运行版本：输入问题后，用 `app/core.mjs` 中的保守规则寻找内置线索；结果显示标题、DOI、许可、原文链接和位置。你打开原文核对，自己写判断与局限，勾选核对声明后保存。卡片可删除、导出 Markdown。

程序没有调用大模型或联网抓取论文，也不会自动断定某个科学结论为真。卡片只存在当前浏览器的 `localStorage`，清除该浏览器数据就会消失；没有账号和云同步。勾选声明也只是创建者自我确认，系统无法证明其真的读过原文。

### 5. 保留失败基线，再依据失败迭代

先固定 [30 道题](../evals/questions.csv)：21 道预期返回指定证据 ID，9 道预期不返回来源；标注依据见[核对说明](../evals/annotation-notes.md)。[基线逐题结果](../evals/results-baseline.json)是 **18/30**：可回答题 10/21、无来源题 8/9。失败主要来自资料/问法覆盖不足，以及一次把 BraSyn 排名问题错配到任务介绍。

随后增加 4 条有原文位置的线索，收紧越界问题的拒答规则，并让卡片保留更多来源字段。[同一题集的改进版结果](../evals/results-improved.json)为 **30/30**；另一个作者设计的[16 道边界题](../evals/challenge.csv)结果为 [16/16](../evals/results-challenge.json)。之后加入手动来源流程，再跑同一批题，结果仍分别是 30/30 和 16/16。逐题 JSON 是真实脚本输出；评分规则只检查返回的证据 ID 或是否拒答，**不自动判断卡片内容是否被原文支持**。题目由项目作者设计，改进也参考了题集，不能当成独立盲测或泛化证明。

### 6. 让固定资料之外的问题仍可走完流程

内置规则只覆盖 8 条线索。现在任何查询下都可以“手动登记已核对的公开来源”：填写论文标题、HTTPS 原文链接、具体位置，以及可选 DOI、许可和备注。程序只做格式校验，并用 `USER-` 标记该来源**未经系统核验**；后续仍须写判断、勾选核对声明才可保存。这样可以处理新的研究问题，但不是自动文献导入或验证。三屏原型的无答案页也提供跳转到此流程的入口。

### 7. 用 Git 保留过程并发布

本地仓库的 `main` 跟踪 GitHub 的 `origin/main`。每一轮文件变化作为一个 Git 提交保存，再同步到 [GitHub 仓库](https://github.com/YeY-zi/research-evidence-workbench)。提交哈希是那一轮文件状态的编号，可以回看当时做了什么，并比较前后差异；GitHub 上的文件不是从零覆盖生成的一份最终稿。

| 提交前缀 | 那一轮主要内容 |
| --- | --- |
| `1373df2` | 科研记录骨架和使用约定。 |
| `b03d576` | 产品问题、PRD、原型与首版演示。 |
| `44e2cdd` | 有出处的二手研究、竞品桌面研究及离线基线。 |
| `c842347` | 扩充内置线索、收紧规则和卡片来源字段。 |
| `9414bef` | 保存改进版评测与产品案例。 |
| `13c4f54` | 手动公开来源的建卡路径。 |

在仓库根目录运行 `git log --oneline -7` 可看最近提交；`git status` 可看是否还有未提交改动。GitHub 仓库保存文档和源代码，用户浏览器里的证据卡片不会自动上传到 GitHub。

## 你可以亲手走一遍

本地已存在仓库时，在它的根目录打开 PowerShell：

```powershell
python -m http.server 8000
```

打开 `http://localhost:8000/app/`。如果电脑没有 Python 3，先安装或使用已有的本地静态服务器；直接双击 HTML 可能受浏览器模块加载限制。

1. 点击“BraTS 2023 模态”→ 查看线索与 DOI → 点击“打开原文”。
2. 在原文中核对对应位置，再点击“用此来源建卡”→ 用自己的话写判断和局限 → 勾选自我核对声明 → 保存并导出 Markdown。
3. 点击“无答案示例”，观察系统提示“当前示例资料未找到”。这表示**内置资料没有可定位线索**，不是证明世界上不存在答案。
4. 如果你自己已经找到另一篇公开论文，展开手动登记，填写准确链接和位置；卡片会显示 `USER-` 标记。此时内容与许可都由你负责核对。

可在仓库根目录运行 `node --test app/core.test.mjs` 检查核心逻辑。想复跑固定题集而不改写仓库内保存的历史结果，可用：

```powershell
node evals/run.mjs self-check "$env:TEMP\workbench-check.json" evals/questions.csv
```

需要 Node.js 才能运行这些检查；浏览器演示本身无需 Node.js。GitHub 保存的是源代码和文件，**当前没有 GitHub Pages 在线演示**，所以应在本地启动服务。每次演示结束可用 `Ctrl+C` 停止服务。

## 目录该怎么看

| 目录 | 用途 | 是否已有真实项目数据 |
| --- | --- | --- |
| `research/` | 公开二手研究、访谈提纲、竞品框架 | 有公开来源整理；没有本项目真实访谈或竞品同题实测。 |
| `product/` | 问题定义、PRD、流程和决策 | 有明确设计与待验证假设。 |
| `prototype/` | 三屏可点击交互草图 | 已完成。 |
| `app/` | 不依赖 API Key 的本地演示 | 已完成受控资料上的最小闭环。 |
| `evals/` | 题集、单人标注依据、脚本和逐题运行结果 | 有真实离线程序结果；没有用户试用指标。 |
| `case-study/` | 面向招聘的产品案例 | 已写实践与局限；真实迭代成效待补。 |
| `docs/`、`templates/`、`records/` | 科研记录工作流与模板 | 骨架保留；不代表已经做过科研实验或复现。 |
| `data/` | 数据来源与许可说明 | 有示例论文说明；没有共享原始医学数据。 |

## 面试时如何准确介绍

> 我提出了一个面向研究证据整理的 AI4Science 产品方向，并借助 Codex 完成了个人作品集原型。第一阶段只聚焦“问题、原文来源、证据卡片”，用两篇公开综述和 8 条人工线索做可追溯演示。我先设计 30 道离线题，保留了 18/30 的基线；依据失败增加资料与规则后，同一题集为 30/30，并补了一个手动登记公开来源的路径。这些是受控程序结果，不是用户测试或 AI 准确率。下一步需要真实研究者访谈、独立标注和未见题验证。

如果被问“AI 在哪里”：目前**没有接入 AI 模型**。AI4Science 是目标场景，现阶段验证的是产品工作流和证据可追溯性；自动检索/抽取是否值得做，应由用户任务和质量评测决定。如果被问“谁做了这些”：如实说明你提出目标、范围和协作要求，具体资料整理、文档、代码、检查与 GitHub 发布由 Codex 辅助完成；不要称自己亲自完成了尚未进行的访谈、编码或独立评测。

## 接下来真正需要你做的事

1. 按[访谈提纲](../research/interview-guide.md)招募目标用户，先取得同意，再观察他们如何核对一篇论文；记录匿名原话、失败和与你原假设相反的例子。
2. 请不参与开发的人复核题目标签、原文位置和卡片判断；增加你没有用来调规则的新问题。
3. 用[同题框架](../research/competitor-review.md)亲自测试替代工具，保留版本、输入和原始输出；再决定下一阶段的自动化范围。
4. 有真实验证后更新 [PRD](../product/PRD.md)、[评测方案](../evals/plan.md)、[案例](../case-study/portfolio-case.md)与首页的完成状态。不要把计划改写成已完成事实。
